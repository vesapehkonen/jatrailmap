# JaTrail VPS deployment

JaTrail runs on one self-managed Ubuntu VPS. Application source code is never
cloned or stored on the server. GitHub builds FastAPI and publishes it to GHCR;
three manually triggered GitHub Actions bootstrap and deploy the VPS.

The existing container-publishing workflow is independent and unchanged.

## Architecture

```text
GitHub repository and Actions
  ├─ build/test FastAPI and publish GHCR image
  ├─ Bootstrap VPS: send one bootstrap script
  ├─ Deploy Stack: send an allowlisted deployment bundle
  └─ Deploy Backend: invoke the installed backend script

/srv/jatrail on the VPS
  ├─ deploy/
  │  ├─ compose.yaml                 managed by Deploy Stack
  │  ├─ Caddyfile                   managed by Deploy Stack
  │  ├─ mongo-init/                 managed by Deploy Stack
  │  ├─ scripts/                    managed by Deploy Stack
  │  ├─ jatrail.env                 created by Deploy Stack if missing
  │  ├─ caddy.env                   created manually on VPS
  │  ├─ image.env                   managed deployment state
  │  ├─ .deployed-image             managed deployment state
  │  └─ secrets/                    generated by Bootstrap, VPS-local
  └─ backups/                       local compressed MongoDB archives
```

Only Caddy publishes ports. FastAPI stays on the proxy network and MongoDB on
the internal backend network. Named volumes retain MongoDB and Caddy data.

## GitHub production environment

Create a GitHub Actions environment named `production` and add these secrets:

```text
VPS_HOST
VPS_USER
VPS_SSH_PRIVATE_KEY
VPS_SSH_HOST_KEY
```

`VPS_SSH_HOST_KEY` contains a complete, previously verified known-hosts line,
not merely a fingerprint. For example, obtain the candidate directly from the
VPS console and verify it before saving it:

```bash
ssh-keyscan -H YOUR_VPS_HOST
```

These are deployment transport credentials. MongoDB passwords and JaTrail
runtime configuration are never stored in GitHub.

The SSH user must already exist and have passwordless `sudo` for Bootstrap VPS.
After bootstrap, subsequent workflows use Docker through membership in the
`docker` group.

## 1. Bootstrap VPS

Run **Bootstrap VPS** manually from GitHub Actions. It supports fresh Ubuntu
22.04, 24.04, and 26.04 servers and follows Docker's official apt-repository
installation. It installs Docker Engine, the Compose plugin, curl, and required
certificates; enables Docker; adds `VPS_USER` to the Docker group; and creates:

```text
/srv/jatrail/deploy/secrets
/srv/jatrail/deploy/scripts
/srv/jatrail/deploy/mongo-init
/srv/jatrail/backups
```

It does not copy Compose, authenticate to GHCR, or start containers. Open a new
SSH session after bootstrap so group membership applies.

Bootstrap also creates these files when they do not already exist:

```text
/srv/jatrail/deploy/secrets/mongo_root_username
/srv/jatrail/deploy/secrets/mongo_root_password
/srv/jatrail/deploy/secrets/mongo_app_username
/srv/jatrail/deploy/secrets/mongo_app_password
```

The default usernames are `jatrail-admin` and `jatrail-app`. Passwords are
independently generated with `openssl rand -base64 48`. Rerunning Bootstrap
preserves every existing credential file and never rotates it. Credentials are
created directly on the VPS and are not returned to or stored by GitHub.

## 2. Create runtime configuration manually

Create the Caddy environment file manually from the example contents before
running Deploy Stack:

```text
deploy/examples/caddy.env    -> /srv/jatrail/deploy/caddy.env
```

Deploy Stack creates `jatrail.env` from `deploy/examples/jatrail.env` when it is
missing and preserves it thereafter. Its defaults use `jatrail.com`, secure
cookies, and the documented account/upload quotas. If deploying another domain,
create or edit `jatrail.env` before rerunning the stack workflow.

Bootstrap has already generated MongoDB credentials. Inspect their presence
without printing their contents:

```bash
find /srv/jatrail/deploy/secrets -maxdepth 1 -type f \
  -printf '%f %m bytes=%s\n' | sort
```

The directory prevents other host users from traversing it. Files are mode
`0644` because local Compose secret mounts preserve host ownership and the
unprivileged containers must be able to read them.

You may replace the generated usernames or passwords after Bootstrap but before
the first stack deployment. After MongoDB has initialized, changing the root
credential file alone does not rotate the database root password and will break
authentication; later rotation must update MongoDB and the corresponding file
together.

Deployment workflows verify these files but never upload, replace, or delete
them. If the GHCR package is private, authenticate once manually:

```bash
docker login ghcr.io
```

## 3. Deploy Stack

Run **Deploy JaTrail stack** manually with either `latest` or a full lowercase
40-character image commit SHA. A SHA is recommended for production.

The workflow checks out source only on the GitHub runner. It creates a tarball
from this explicit allowlist:

```text
deploy/compose.yaml
deploy/Caddyfile
deploy/examples/jatrail.env
deploy/mongo-init/01-create-app-user.sh
deploy/scripts/common.sh
deploy/scripts/verify_runtime.sh
deploy/scripts/deploy_stack.sh
deploy/scripts/deploy_backend.sh
deploy/scripts/backup_mongodb.sh
deploy/scripts/install_bundle.sh
```

It copies the archive to `/tmp`, installs only managed files under
`/srv/jatrail/deploy`, removes the temporary archive, and runs `deploy_stack.sh`.
If `/srv/jatrail/deploy/jatrail.env` does not exist, the installer creates it
from the bundled production defaults for `jatrail.com`. An existing file or
symlink is always preserved. Caddy configuration, secrets, image state,
backups, and named volumes are not overwritten.

Stack deployment pulls MongoDB, Caddy, and the selected FastAPI image; starts
MongoDB; waits with lightweight process inspection for first-run initialization
to finish; runs one authenticated ping; synchronizes the application database
account in a separate `mongosh`; and starts FastAPI and Caddy. It retries the
complete public `/health` endpoint while Caddy obtains its first certificate.

MongoDB is pinned to `7.0.39-jammy` because MongoDB 8 cannot start on the
target's affected Linux kernel. Resource ceilings total 480 MB and one CPU.
MongoDB has no recurring health check so two `mongosh` processes do not compete
inside its 352 MB limit.

## 4. Deploy Backend

Run **Deploy JaTrail backend** manually for normal FastAPI releases. It accepts
`latest` or a full image commit SHA. The workflow does not check out or upload
repository files. It invokes the already installed script on the VPS.

The script pulls the selected FastAPI image and runs Compose with `--no-deps`,
replacing only `jatrail-web-1`. It does not pull, restart, recreate, or modify
MongoDB or Caddy. It waits for web container health and the public `/health`.
Failure is reported to GitHub and left in place; there is no automatic rollback.

## Manual inspection

SSH to the VPS and use:

```bash
cd /srv/jatrail/deploy
docker compose --env-file image.env -f compose.yaml ps
docker compose --env-file image.env -f compose.yaml logs --tail=200 caddy web mongo
docker stats --no-stream
cat .deployed-image
```

No workflow deletes old images or performs image retention.

## MongoDB backups

Only MongoDB is backed up. Docker volumes, source code, Caddy state,
certificates, and other files are excluded. Run manually:

```bash
/srv/jatrail/deploy/scripts/backup_mongodb.sh
```

Defaults are `/srv/jatrail/backups` and 14-day retention. Override them for one
run:

```bash
JATRAIL_BACKUP_DIR=/srv/jatrail/backups \
JATRAIL_BACKUP_RETENTION_DAYS=30 \
/srv/jatrail/deploy/scripts/backup_mongodb.sh
```

To restore, stop FastAPI, select the archive deliberately, and keep MongoDB
running:

```bash
cd /srv/jatrail/deploy
docker compose --env-file image.env -f compose.yaml stop web

docker compose --env-file image.env -f compose.yaml exec -T mongo sh -ec '
  mongorestore \
    --host 127.0.0.1:27017 \
    --username "$(cat /run/secrets/mongo_app_username)" \
    --password "$(cat /run/secrets/mongo_app_password)" \
    --authenticationDatabase jatrail \
    --nsInclude "jatrail.*" \
    --drop --archive --gzip
' < /srv/jatrail/backups/jatrail-YYYYMMDDTHHMMSSZ.archive.gz

docker compose --env-file image.env -f compose.yaml start web
```

## Migrating the old repository-based VPS

The current Compose project name remains `jatrail`, so named volumes survive
the layout migration.

1. Run and copy a MongoDB backup off the VPS.
2. Stop the current stack without deleting volumes.
3. Preserve the old checkout recoverably:

   ```bash
   sudo mv /srv/jatrail /srv/jatrail-source-legacy
   ```

4. Run **Bootstrap VPS**.
5. Copy only `jatrail.env`, `caddy.env`, `secrets/`, and any backup archives from
   the legacy directory into the new `/srv/jatrail` layout.
6. Run **Deploy JaTrail stack**.
7. Verify login, trails, photos, and `/health`.
8. Remove `/srv/jatrail-source-legacy` manually only after successful recovery
   testing and only when it contains nothing still needed.

The workflows never delete the old checkout automatically.
